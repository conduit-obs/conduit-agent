# ADR-0022 — Scope RED derivation to request-like spans; carry stable + legacy HTTP semconv dimensions

- **Status**: Accepted
- **Date**: 2026-06-14
- **Deciders**: Tech Lead
- **Context**: M8 derives RED metrics from spans with the upstream `spanmetricsconnector` (ADR-0006), teed off the traces pipeline before any sampling (ADR-0005). Two gaps surfaced when the implementation was validated against the RED product intent ("Rate / Errors / Duration for serviced application requests").

  1. **Every span produced a request count.** The connector emits its `calls` counter and `duration` histogram for *every* span it receives — there is no built-in span-kind filter. The M8 wiring teed the connector off the main traces pipeline, so `CLIENT`, `INTERNAL`, and `PRODUCER` spans (outbound calls, in-process work, queue publishes) were counted as "requests" alongside the `SERVER` / `CONSUMER` spans that actually represent inbound serviced requests. Rate and error figures were inflated by work that isn't a request. The product intent is explicit that a non-request span should not emit RED metrics.

  2. **Only legacy HTTP semconv attribute names were dimensioned.** The default span-dimension set listed `http.method` and `http.status_code` — the pre-1.23 HTTP conventions. Applications instrumented with a current OTel SDK (semconv ≥ 1.23, stable since) emit `http.request.method` and `http.response.status_code` instead, so those services rendered *empty* HTTP method / status dimensions on their RED metrics.

  The fix for (1) cannot simply add a filter to the existing traces pipeline: that pipeline ships spans to Honeycomb, and dropping non-request spans there would violate the preserve-the-original-telemetry principle (rich wide traces stay intact; metrics complement them). The fix for (2) cannot just swap legacy → stable names, because a Conduit fleet runs a mix of SDK versions and both name sets must populate.

- **Decision**: Conduit V0.x makes two changes to the RED-from-spans path, both confined to the curated default set and the rendered Collector pipeline (no new escape hatch, no custom component — `filterprocessor` is already in `builder-config.yaml`).

  1. **Dedicated `traces/red` pipeline with `filter/red_requests`.** RED no longer tees the `span_metrics` connector off the main `traces` pipeline. Instead the expander renders a second traces pipeline, `traces/red`, that:
     - shares the same receiver set as the main traces pipeline (`otlp`, plus `obi` when enabled) — an OTel receiver fans its stream out to every pipeline that lists it, so RED still sees 100% of spans before any downstream sampler (ADR-0005 preserved);
     - runs the same resource-shaping processors as the main pipeline (`memory_limiter`, `resourcedetection`, `k8sattributes` when on k8s, `resource`) so the connector's `resource_metrics_key_attributes` resolve identically;
     - applies a new `filter/red_requests` processor that keeps a span only when `kind == SPAN_KIND_SERVER or kind == SPAN_KIND_CONSUMER` (expressed as the drop condition `kind != SPAN_KIND_SERVER and kind != SPAN_KIND_CONSUMER`, `error_mode: ignore`);
     - exports to `span_metrics` as its only exporter.

     The main `traces` pipeline is unchanged except that it no longer lists `span_metrics` in its exporters — it ships every span (all kinds) to Honeycomb / Refinery untouched. The connector remains a receiver on the `metrics` pipeline where the derived RED metrics surface.

  2. **Both stable and legacy HTTP method / status-code dimensions.** `REDDefaultSpanDimensions` adds `http.request.method` and `http.response.status_code` alongside the existing `http.method` and `http.status_code`. The connector omits a configured dimension from a series when the span lacks that attribute (no `default` is set), so a stable-semconv span contributes the stable dimensions and leaves the legacy ones absent, and a legacy span the reverse — listing both does not create empty-string cardinality fan-out. Error state continues to come from the connector's built-in `status.code` (span status) dimension plus the HTTP status-code dimensions; no separate error counter is introduced (the connector does not emit one, and a dimensioned `calls` counter is the OTel-idiomatic RED error signal).

- **Alternatives considered**:
  - **`filter` on the main traces pipeline.** Rejected: it would drop non-request spans from the Honeycomb trace stream, defeating the "rich traces for troubleshooting, deterministic metrics for health" split that is the whole point of RED-from-spans.
  - **`forward` connector to fan the main traces stream into a filtered RED pipeline.** Rejected as unnecessary indirection — a shared `otlp` receiver already fans out to multiple pipelines natively, with no extra connector to reason about.
  - **Replace legacy HTTP dimension names with stable ones.** Rejected: a real fleet runs mixed SDK versions; dropping the legacy names would blank the HTTP dimensions for every service still on pre-1.23 instrumentation. Carrying both is cheap (bounded cardinality) and version-agnostic.
  - **Keep deriving from all spans and let operators filter by `span.kind` at query time.** Rejected: it pushes a correctness concern (what counts as a request) onto every dashboard and alert, and the inflated `calls` total is the number most consumers read first. Deterministic server/consumer scoping at derivation time is the honest default.
  - **Add `db.system` / `messaging.destination.name` in the same change.** Deferred: out of scope for this ADR, which is about request-span scoping and HTTP semconv currency. Database request-style spans remain an explicit opt-in per ADR-0006's stance.
  - **Rename the emitted metrics to an `app.request.*` scheme (`app.request.count` / `app.request.error.count` / `app.request.duration`).** Rejected. The connector already emits under its standard namespace — `traces.span.metrics.calls` (request counter) and `traces.span.metrics.duration` (latency histogram) — which is the conventional, ecosystem-recognized span-metrics naming and is what all five checked-in `dashboards/*.json` query. Renaming would break every shipped board and the demo flow while regressing away from the standard span-metrics names. The product spec explicitly permits "where OpenTelemetry semantic metric names are already standardized and appropriate, prefer those names," and these are. RED error rate is read off the request counter via the `status.code` / HTTP status-code dimensions (`calls` where `status.code = STATUS_CODE_ERROR`), so no distinct `error.count` instrument is needed — and the upstream `spanmetricsconnector` cannot emit one without bolting on a second connector (e.g. `countconnector`), which would duplicate an existing signal and add a build dependency for no analytical gain.

- **Consequences**:
  - **Schema work.** `internal/config/types.go` extends `REDDefaultSpanDimensions` with `http.request.method` and `http.response.status_code` (interleaved with their legacy forms). No new curated knob; the denylist is unchanged.
  - **Expander work.** `internal/expander/expander.go` stops appending `span_metrics` to the main traces pipeline exporters and instead populates `REDTraceProcessors` (the main traces processor list with `filter/red_requests` spliced in before `batch`, per ADR-0016) for the new pipeline. `internal/expander/templates/base.yaml.tmpl` renders the `filter/red_requests` processor and the `traces/red` pipeline, both gated on `REDEnabled` (so RED-off and `obi.replace_span_metrics_connector: true` renders are unaffected). All nine RED-on goldens regenerate; the RED-off golden (`10-no-profile-red-off`) is unchanged.
  - **Tests.** `internal/expander/expander_test.go` asserts the main traces pipeline does NOT carry `span_metrics` or `filter/red_requests`, that `traces/red` exports to `span_metrics` only and runs the filter, that the new dimensions render, and that RED-off / OBI-replace renders omit the filter and the `traces/red` pipeline entirely.
  - **Behavior change: request counts drop to request-only.** Operators upgrading will see `calls` / `duration` series for `SERVER` / `CONSUMER` spans only — rate and error counts fall to the true serviced-request population. This is a correctness improvement; release notes call it out because dashboards that previously included client/internal spans will show lower (accurate) request rates.
  - **Cardinality.** Adding two bounded HTTP dimensions has negligible fan-out (method and status-code are small enumerations); the `aggregation_cardinality_limit` guardrail (ADR-0006) is unchanged.
  - **Memory-limiter caveat (unchanged).** Both traces pipelines run `memory_limiter` first; under memory pressure spans may be refused before the connector sees them, dropping traces and RED together — acceptable and identical to the prior single-pipeline behavior.
