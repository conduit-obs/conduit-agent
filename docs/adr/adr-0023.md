# ADR-0023 — Credentialed `integrations:` block for multi-target pull receivers (MSSQL first)

- **Status**: Proposed
- **Date**: 2026-06-15
- **Deciders**: Tech Lead
- **Context**: Every receiver Conduit ships today is either *always-on* (`otlp`) or a *zero-input platform fragment* (`hostmetrics`, `journald`, `filelog`, `kubeletstats`, `windowseventlog`) selected by `profile.mode`. None of them take operator input beyond an on/off toggle, and none of them connect *out* to a credentialed endpoint. The expander reflects this: profiles are static YAML fragments spliced under `receivers:` (one instance per signal per platform), and the curated schema has no place to express "connect to *these three* SQL Server instances with *these* credentials."

  The most-requested integrations from the field — Microsoft SQL Server (`sqlserverreceiver`), PostgreSQL, MySQL, Redis — break that mold in three ways at once:

  1. **They are pull receivers with a connection target.** Each needs an endpoint (`host:port`), almost always credentials, and per-target TLS settings. This is operator-supplied data, not a platform default.
  2. **There are N of them.** A host or cluster routinely runs several database instances; the operator wants one Conduit agent scraping all of them. The renderer must emit *N receiver instances* (`sqlserver/primary`, `sqlserver/reporting`, …), which the static one-fragment-per-signal model cannot do.
  3. **They carry secrets.** A connection password cannot live inline in `conduit.yaml` (it ends up in ConfigMaps, `conduit preview` output, support bundles). Secrets must be referenced, never embedded.

  None of these receivers is in `builder-config.yaml` today (ADR-0004: "pure upstream components, compiled deliberately"), so even the `overrides:` escape hatch (ADR-0012) cannot reach them — the components aren't in the binary. So this is simultaneously a *build* decision (which components ship) and a *schema* decision (the first credentialed, multi-instance, operator-configured receiver surface Conduit has had).

- **Decision**: Introduce a new top-level `integrations:` block in `conduit.yaml` — a curated, credentialed, multi-target surface for pull receivers — and compile the first cohort of database receivers into the binary. The block is the third kind of receiver source alongside the always-on `otlp` and the `profile`-selected platform fragments.

  **Schema shape.** `integrations:` holds one keyed list per integration type; each entry is a named instance:

  ```yaml
  integrations:
    sqlserver:
      - name: primary                 # → receiver id sqlserver/primary
        endpoint: "10.0.0.4:1433"
        username: "conduit_ro"
        password: "${env:MSSQL_PRIMARY_PASSWORD}"   # ${env:...} only — see below
        tls:
          insecure: false
        collection_interval: 30s      # optional; defaults to 30s
    postgresql:
      - name: orders
        endpoint: "orders-db:5432"
        username: "conduit_ro"
        password: "${env:PG_ORDERS_PASSWORD}"
        databases: ["orders"]
  ```

  Each list element renders to one upstream receiver instance (`<type>/<name>`) and is wired into the **metrics** pipeline (these receivers emit metrics; `sqlqueryreceiver` may also emit logs and is wired accordingly). The expander gains a third receiver-id source feeding `MetricReceivers` / `LogReceivers`, parallel to the existing platform-fragment path.

  **First cohort (compiled into `builder-config.yaml`).** `sqlserverreceiver` (MSSQL — the lead ask), `postgresqlreceiver`, `mysqlreceiver`, `redisreceiver`, and `sqlqueryreceiver` (the generic custom-SQL escape hatch that turns any supported driver into metrics/logs). They share an almost identical config shape (endpoint + username + password + tls + collection_interval), which is why they land as one cohort behind one schema rather than five bespoke blocks.

  **Secret handling — `${env:...}` only.** The `password` (and any future secret-bearing field) MUST be an OTel `${env:NAME}` reference; the validator rejects an inline literal that does not match the `${env:...}` shape. This mirrors how `output.honeycomb.api_key` already works and keeps plaintext credentials out of the rendered config, `conduit preview`, ConfigMaps, and support bundles. The agent process resolves the env var at startup; on Kubernetes the Helm chart threads it in via `extraEnv` → `secretKeyRef` (the same path already used for vendor OTLP tokens).

  **Cardinality + curated surface.** Like every other Conduit knob, the block is a *thin* typed surface: the fields above plus per-type essentials (e.g. `databases:` for Postgres, `metrics:` enable/disable maps deferred to `overrides:`). Anything the upstream receiver supports beyond the curated fields goes through `overrides.receivers.<type>/<name>.<...>` (ADR-0012), deep-merged over the rendered instance. ADR-0012's "promote knobs when patterns emerge" governs growth.

- **Alternatives considered**:
  - **Use `overrides:` only (no first-class block).** Rejected on two counts: (a) the receivers aren't compiled in, so overrides can't reach them regardless; and (b) credentialed multi-target scraping is exactly the kind of repeated pattern ADR-0012 says should be promoted to a typed field — pushing every operator to hand-write `receivers:` + `service.pipelines.metrics.receivers:` overrides (restating the full list, since lists replace) is the failure mode the curated schema exists to prevent.
  - **A new `profile.mode` per database (e.g. `mode: mssql`).** Rejected: `profile.mode` is a single-valued OS/platform selector ("this agent runs on linux / k8s"), and databases are orthogonal to platform (you scrape MSSQL *from* a linux host or a k8s pod). Overloading `profile.mode` would make "linux host that also scrapes two SQL Servers" inexpressible.
  - **Fold targets under `metrics:` (next to `metrics.red` / `metrics.prometheus`).** Rejected: `metrics:` is the derived-/scraped-metric *tuning* umbrella; a credentialed connection target is a different kind of thing (it has lifecycle, auth, TLS, and may emit logs as well as metrics via `sqlqueryreceiver`). A distinct top-level `integrations:` block reads correctly and leaves room for non-metric integrations later.
  - **Inline credentials with a redaction pass on `preview`.** Rejected: redacting after the fact is fragile (one missed code path leaks the secret), and the credential would still sit in the on-disk ConfigMap. `${env:...}`-only is the only honest contract.
  - **Ship all database receivers but gate behind a build tag.** Rejected for V1 simplicity: the cohort is small, the binary-size delta is acceptable, and a single build keeps the release matrix (ADR-0003/0019) unchanged. Revisit if the integration list grows large enough to justify a "lite" distribution.

- **Consequences**:
  - **Build.** `builder-config.yaml` gains five contrib receivers (`sqlserver`, `postgresql`, `mysql`, `redis`, `sqlquery`). Binary size and dependency surface grow; the compatibility table (`docs/release/compatibility.md`) and `conduit version` component list update accordingly. Each pins to the same upstream MINOR as the rest of the distribution (ADR-0014).
  - **Schema work.** `internal/config/types.go` gains an `Integrations` struct and per-type instance structs; `validate.go` enforces name uniqueness per type, required endpoint, and the `${env:...}`-only secret rule; `load.go` defaults `collection_interval`.
  - **Expander work.** A third receiver-id source. Unlike platform fragments (static files) and unlike OBI (a single inline block), integration instances are *operator-data-driven N-instance* renders — the expander iterates the lists and emits `<type>/<name>` blocks, appending each id to the right pipeline. This is the first renderer path whose receiver *count* depends on user input; the golden matrix gains a multi-instance case.
  - **Secrets / deploy.** Docs and the Helm chart document the `extraEnv` → `secretKeyRef` pattern for database passwords. No secret ever reaches the rendered config.
  - **Doctor.** A future `CDT06xx integrations.reachable` check can TCP-probe each integration endpoint (parallel to `CDT0101 output.endpoint_reachable`), and `CDT0102`-style "password present" validation. Reserved, not built in this ADR.
  - **Scope discipline.** This is a deliberate widening of the "tiny curated schema" stance (ADR-0004 / ADR-0007). It is justified because credentialed database monitoring is a top field ask that the escape hatch structurally cannot serve, and the surface stays thin (connection essentials only; everything else via `overrides:`).
